# 4 系统总体设计

## 4.1 总体架构

依据“业务数据库和对象存储不持久化明文、文件密钥与用户身份私钥”的数据边界，以及 KGC 逻辑隔离要求，系统采用三域架构，如图4.1所示。

![图 4.1 系统总体架构](images/fig4-1-architecture.png)

三端职责与安全边界如下：

（1）**浏览器加密端**：文件明文只在该端完成加解密。文件加密、元数据加密、密钥信封封装、下载校验与解密由浏览器密码模块执行；KGC 生成的 SM9 私钥包经应用接口返回后保存在本地 IndexedDB，业务数据库不保存该私钥。当前 IndexedDB 中的私钥包为 Base64 编码而非设备硬件密钥保护，这是需要进一步加固的本地安全边界。

（2）**应用服务器（盲存储）**：负责认证、授权、密文分块与信封的存取、KGC 代理、审计和安全事件。文件数据面持久化的内容是密文分块、SM4 加密的元数据和 SM9 密钥信封；密钥初始化时，服务器会在 HTTP 响应对象中短暂转发 KGC 返回的私钥包。由于服务器持有 KGC 服务令牌并可访问密文，本文将其列入可信控制面，不能宣称应用服务器完全失陷后仍必然无法解密。

（3）**KGC 密钥中心**：独立 Spring Boot 服务（端口 8081），持有 SM9 加密主私钥并按身份提取用户私钥。主私钥以加密文件形式落盘，解封后只在 KGC 进程内使用；对外暴露主公钥查询和经服务令牌鉴权的签发类接口。开发环境采用独立 H2 内存库，生产配置指向独立 MySQL 数据库。

该分域首先降低数据库、对象存储和只读备份泄露造成的明文风险。KGC 单独失陷时能够提取身份私钥，但通常还需取得应用侧密文；应用服务器完全失陷时则可能同时访问密文、信封和 KGC 服务令牌，超出当前方案已解决的威胁范围。因此，三域设计提供的是职责隔离和攻击面收缩，而不是对任意单点完全失陷的无条件安全保证。

## 4.2 端到端加密数据流设计

### 4.2.1 发送流程

发送方浏览器执行“获取主公钥—生成密钥—分块加密—封装信封—分块上传”流程。浏览器不直接访问 KGC，主公钥和私钥签发均由应用服务器代理，发送时序如图4.2所示。

![图 4.2 发送端到端加密时序](images/fig4-2-send-sequence.png)

### 4.2.2 接收流程

接收方执行逆过程：查询收件列表，取回属于自己的密钥信封，以本地 SM9 私钥解封得到 DEK；逐块下载密文，先按响应头中的 SM3 摘要复核，再以 DEK 与分块 IV 执行 SM4 解密；全部分块解密后在浏览器内拼装文件并还原元数据。任一分块摘要失配即中止。该摘要机制可发现传输损坏和只改密文的篡改，但恶意服务端若同步替换密文与摘要仍可能绕过，因此后续应采用 SM4-GCM 或基于独立认证密钥的 MAC。若接收方更换设备，可通过重签发取得由同一身份确定的私钥；恢复历史密文的前提是 KGC 主密钥未改变且已可靠备份。

## 4.3 数据库设计

系统数据库共 11 张表：10 张核心业务表与 1 张安全事件表，如表 4.1 所示。

表 4.1 数据库表清单

| 表名 | 作用 | 主键 |
|---|---|---|
| roles | 角色定义（RBAC） | 自增 id |
| users | 用户账号（仅存 BCrypt 口令哈希） | 自增 id |
| user_roles | 用户—角色多对多 | 自增 id |
| user_keys | 用户 SM9 身份标识与密钥状态（不存私钥） | 自增 id |
| kgc_private_key_issues | KGC 私钥签发审计流水 | UUID |
| files | 文件投递主记录（元数据已加密） | UUID |
| file_chunks | 密文分块记录（含 SM3 摘要） | 自增 id |
| file_recipients | 接收人与其 SM9 密钥信封 | 自增 id |
| audit_logs | 审计日志（含哈希链字段） | 自增 id |
| login_attempts | 登录失败聚合与限流 | 自增 id |
| security_events | 安全事件告警 | 自增 id |

实体关系如图 4.3 所示：users 与 user_keys 一对一（一人一身份），files 经 file_chunks 一对多承载密文分块、经 file_recipients 一对多关联接收人；审计类表（audit_logs、kgc_private_key_issues、login_attempts、security_events）刻意不设指向业务表的硬外键，保证用户删除后审计仍可独立追溯，且登录限流表可记录不存在的用户名（爆破尝试）。

盲存储红线在数据模型上的落实如表 4.2 所示：数据库绝不保存文件明文、明文文件名、SM4 密钥明文与用户 SM9 私钥。

表 4.2 敏感数据存储策略

| 存储位置 | 实际存储内容 | 谁能解开 |
|---|---|---|

## 4.4 安全机制设计

（1）**认证与会话**：用户名口令经 BCrypt 校验，会话基于 Spring Security 的 HttpSession 机制，跨域仅放行白名单前端源并携带凭证；登录失败按账号计数锁定、按 IP 限流。

（2）**方法级 RBAC**：管理与审计接口以 @PreAuthorize 声明角色约束，未认证返回统一 401、越权返回统一 403 JSON，并在过滤器级与方法级双重埋点记录越权事件。

（3）**审计哈希链**：每条审计记录的链哈希按式(4.1)计算：

$$H_i = SM3(H_{i-1} \parallel C_i) \tag{4.1}$$

其中 $C_i$ 为第 $i$ 条记录的规范化内容串，$H_0$ 为创世哈希。修改参与哈希的字段或删除、重排链中间记录会破坏后续链接，校验接口可以逐条重算并定位首个断点。当前规范化串未覆盖 userAgent，哈希链也未发布外部锚点，因此链尾删除、整表删除以及未纳入串的字段修改不能由剩余链独立证明。

（4）**双侧摘要校验**：每个密文分块在浏览器与服务器分别计算 SM3，上传与下载两个方向均进行比对，用于发现随机损坏和摘要未同步修改的异常。该设计不具备带密钥的认证完整性，不能抵御控制存储端的攻击者同步替换密文与摘要。

（5）**安全事件**：与“操作面”的审计日志互补，系统面向“攻击面”设置七类安全事件自动埋点，如表 4.3 所示。

表 4.3 七类安全事件

| 事件类型 | 触发场景 | 级别 |
|---|---|---|
| BRUTE_FORCE_LOCK | 口令连续失败达到阈值锁定账号 | 高 |
| IP_THROTTLED | 单 IP 登录频率超限 | 中 |
| ACCESS_DENIED | 越权调用受保护接口（方法级/过滤器级） | 中 |
| UNAUTHORIZED_FILE_ACCESS | 非接收人尝试访问他人文件 | 高 |
| CHUNK_TAMPER_DETECTED | 下载侧发现存储对象与已登记摘要不一致 | 高 |
| OVERSIZED_CHUNK | 分块超出大小上限 | 中 |
| AUDIT_CHAIN_BROKEN | 审计哈希链校验断裂 | 高 |

## 4.5 本章小结

本章完成系统总体设计：三域架构将文件内容运算放在浏览器、密文持久化放在应用服务器、主密钥放在 KGC，并把应用控制面和 KGC 明确纳入可信边界；发送与接收数据流给出密码学处理时序；11 表数据库以盲存储字段策略落实数据边界；安全机制覆盖认证授权、受限能力的审计哈希链、双侧摘要校验和七类安全事件。第 5 章在此基础上展开各模块的详细实现。
