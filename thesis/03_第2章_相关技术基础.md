# 2 相关技术基础

## 2.1 国密算法体系

我国商用密码算法体系覆盖杂凑、对称加密、公钥密码等类别，均已发布为国家标准。本系统使用其中的 SM3、SM4 与 SM9 三种算法，其标准依据与在本系统中的用途如表 2.1 所示。

表 2.1 本系统采用的国密算法

| 算法 | 类别 | 标准依据 | 本系统用途 |
|---|---|---|---|
| SM3 | 密码杂凑 | GB/T 32905—2016[13] | 分块损坏检测、审计哈希链、SM9 内部 H1/KDF |
| SM4 | 分组密码 | GB/T 32907—2016[14] | 文件内容与元数据加密（CBC 模式） |
| SM9 | 标识密码 | GB/T 38635.2—2020[9] | 文件密钥按接收人身份封装（数字信封） |

### 2.1.1 SM3密码杂凑算法

SM3 是我国自主设计的密码杂凑算法，输出长度为 256 比特。算法采用 Merkle-Damgård 迭代结构：消息经填充后按 512 比特分组，每组经 64 轮压缩函数迭代，最终输出 256 比特摘要[13]。本系统在浏览器端与服务端分别计算 SM3，对每个密文分块进行摘要比对，并以 SM3 构造业务审计日志哈希链。需要区分“摘要校验”与“认证完整性”：当前分块摘要未使用独立认证密钥，能够发现随机损坏和只改密文的篡改，但无法阻止恶意存储端同时替换密文与摘要。

### 2.1.2 SM4分组密码算法

SM4 是分组长度与密钥长度均为 128 比特的分组密码算法，采用 32 轮迭代结构，加解密使用相同结构而轮密钥次序相反[14]。本系统采用 SM4 的 CBC 工作模式对文件按块加密：每个分块使用独立随机初始向量（IV），避免相同明文直接产生相同密文；PKCS#7 填充使任意长度数据均可加密。SM4 作为对称算法承担大体积文件内容的加密任务，但 CBC 本身不提供认证，生产化方案应进一步采用带认证模式或“加密后认证”结构。

### 2.1.3 SM9标识密码算法与双线性对

SM9 是基于双线性对的标识密码算法[9][8]。设 $G_1$、$G_2$ 为阶等于素数 $N$ 的加法循环群，$G_T$ 为同阶乘法循环群，$P_1$、$P_2$ 分别为 $G_1$、$G_2$ 的生成元。双线性对 $e: G_1 \times G_2 \rightarrow G_T$ 满足双线性性质：

$$e([a]P, [b]Q) = e(P, Q)^{ab}, \quad \forall a,b \in [1, N-1] \tag{2.1}$$

SM9 选用 256 比特 BN 曲线并采用 R-ate 对实现上述映射[7]。标识密码的核心优势是“身份即公钥”：用户的邮箱、工号等身份标识经杂凑即可派生公钥，无需数字证书。

SM9 加密体系中，密钥生成中心（KGC）随机选取加密主私钥 $ke \in [1, N-1]$，计算加密主公钥：

$$P_{pub\text{-}e} = [ke]P_1 \tag{2.2}$$

主公钥公开发布，主私钥由 KGC 秘密保存。对身份标识为 $ID_B$ 的用户，KGC 计算 $t_1 = H_1(ID_B \parallel hid, N) + ke \bmod N$、$t_2 = ke \cdot t_1^{-1} \bmod N$，签发该用户的加密私钥：

$$de_B = [t_2]P_2 \tag{2.3}$$

其中 $H_1$ 为由 SM3 构造的密码函数，$hid$ 为加密私钥生成函数识别符。可见私钥提取仅需标量点乘，不涉及双线性对运算。

发送方使用接收方身份 $ID_B$ 与主公钥进行密钥封装：随机选取 $r \in [1, N-1]$，计算

$$Q_B = [H_1(ID_B \parallel hid, N)]P_1 + P_{pub\text{-}e} \tag{2.4}$$

$$C_1 = [r]Q_B, \quad w = e(P_{pub\text{-}e}, P_2)^r \tag{2.5}$$

$$K = KDF(C_1 \parallel w \parallel ID_B,\ klen) \tag{2.6}$$

$C_1$ 随密文传输，$K$ 即封装出的对称密钥。接收方以私钥 $de_B$ 解封：

$$w' = e(C_1, de_B), \quad K' = KDF(C_1 \parallel w' \parallel ID_B,\ klen) \tag{2.7}$$

由式(2.1)可验证 $e(C_1, de_B) = e([r \cdot t_1]P_1, [t_2]P_2) = e(P_1, P_2)^{r \cdot ke} = w$，故 $K' = K$，仅持有对应身份私钥的接收方能恢复密钥。本系统利用式(2.4)~式(2.7)的封装/解封机制包装文件密钥，双线性对运算只发生在浏览器端。

## 2.2 混合加密与数字信封机制

公钥密码运算开销大，不适合直接加密大体积文件。混合加密采用“密钥封装机制 + 数据封装机制”（KEM-DEM）的组合：为每个文件随机生成一次性的数据加密密钥（Data Encryption Key，DEK），用高速对称算法加密文件本体，再用公钥算法仅加密这把短小的 DEK，形成“数字信封”。

本系统的信封机制结合 SM9 后具有天然的多接收人优势：文件用 SM4 以 DEK 加密一次，DEK 分别按每位接收人的 SM9 身份标识执行一次密钥封装，生成各自的信封。N 位接收人只需 N 次毫秒级的 SM9 封装，而无需对文件本体重复加密，实现“一份密文、多人接收”。任一接收人以自己的 SM9 私钥解开属于自己的信封获得 DEK，再解密文件。信封之间相互独立，无法互相解开。

## 2.3 KGC与密钥托管风险

KGC 是标识密码体系的信任根：它掌握主私钥，能够为任意身份计算用户私钥，因此标识密码天然存在密钥托管（Key Escrow）问题——KGC 理论上可解密系统内任何密文。工程上必须通过部署与治理手段约束该风险，本系统采取的措施包括：

（1）KGC 独立部署，与应用服务器进程及数据库逻辑隔离；应用服务器通过静态服务令牌代理身份登记和私钥签发请求，因此应用控制面仍属于可信计算基；

（2）主私钥仅以加密形态落盘；生产配置应强制从环境变量注入口令并移除开发环境中的便捷默认值；

（3）私钥签发全程留痕，每次签发（含换设备重签发）均写入流水；当前 KGC 签发流水尚未接入业务审计哈希链，主要提供操作追溯而非密码学不可篡改证明；

（4）签发接口校验“请求身份必须与数据库登记身份一致”，杜绝为伪造身份签发私钥。

此外，KGC 主密钥文件和解封口令必须可靠备份；若主密钥丢失或被重新生成，即使身份字符串不变也无法恢复历史密文。更彻底的分层 KGC、门限化主密钥、应用侧最小权限凭据和人工审批签发等方案作为后续改进方向在结论中讨论。

## 2.4 关键技术选型

系统关键技术选型如表 2.2 所示。

表 2.2 系统关键技术选型

| 层次 | 技术方案 | 选型理由 |
|---|---|---|
| 前端框架 | Vue 3 + Vite | 组合式 API 适合封装加密流程；开发调试高效 |
| 浏览器国密算法 | GmSSL-JS（guanzhi）移植[17] | 纯 JavaScript SM9/SM3/SM4 实现，可在浏览器运行双线性对 |
| 加密执行环境 | WebWorker | 加解密移出主线程，界面不卡顿，逐块反馈进度 |
| 应用服务器 | Spring Boot 3 + Spring Security + MyBatis | 成熟的会话认证与方法级 RBAC；SQL 可控便于审计 |
| KGC 服务 | Spring Boot 独立服务（:8081） | 信任域隔离；原生 Java 实现 SM9 签发（仅点乘，无需配对） |
| 数据库 | H2（开发）/ MySQL 8（生产） | 同一份可移植 SQL 脚本双环境运行 |
| 对象存储 | 本地文件系统 / MinIO 条件切换 | 密文分块盲存储；生产可平滑迁移分布式对象存储 |
| 测试 | JUnit 5 + Node.js 端到端脚本 | 单元/集成与跨端（Java↔JS）互通双重验证 |

选型的核心考量是使文件内容的加解密在浏览器完成，因此浏览器端需要运行真实的 SM9 双线性对运算。GmSSL-JS 提供了可移植的纯 JavaScript 基础实现[17]，本文在其上补充封装逻辑，进行了字节级验证并修复两处实现缺陷（见 5.1 节）。KGC 侧的私钥提取由式(2.3)可知只涉及标量点乘，故采用原生 Java 实现，并与 JavaScript 侧对同一主密钥和身份的输出逐字节比对。

## 2.5 本章小结

本章介绍了系统依赖的密码学与工程技术基础：SM3、SM4、SM9 三种国密算法的原理及其在系统中的分工，基于 KEM-DEM 的数字信封机制及其在 SM9 下的多接收人扩展，KGC 的信任根地位与密钥托管风险的工程约束措施，最后给出了以“浏览器内真 SM9”为核心约束的技术选型。这些基础支撑第 4、5 章的系统设计与实现。
