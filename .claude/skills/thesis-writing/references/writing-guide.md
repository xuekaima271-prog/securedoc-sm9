# 毕业论文写作指南（写什么、怎么写）

> 面向"帮用户写/改论文内容"的任务。格式数字细节见 `format-spec.md`。
> 配套文档：降重与去 AI 味见 `paraphrase-and-humanize.md`；全文审查与一致性检查见 `review-checklist.md`。

## 1. Markdown 源文件约定（本技能的输入格式）

论文以分章 Markdown 存放（如 `thesis/02_第1章_绪论.md`），构建脚本按首个标题自动识别角色：

| 首标题 | 角色 |
|---|---|
| `# 摘要…`（内含 `## 摘要` 与 `## Abstract`） | 摘要页 |
| `# 1 绪论` 等 `# N 标题` | 正文章 |
| `# 结论` | 结论 |
| `# 参考文献` | 文献表（只取 `[n] …` 行） |
| `# 致谢` / `# 附录` | 致谢 / 附录 |

写作时必须遵守的语法约定：

- 标题：`# 1 绪论`、`## 1.1 xxx`、`### 1.1.1 xxx`、`#### xxx`，编号手写、与 # 级数一致。
- **`>` 引用行 = 作者备注**，不会进入 Word 成品——放待办、素材出处、导师意见都用它。
- 表：表题独立成段写在表格前一行，格式 `表 2.1 表题文字`；随后紧跟 Markdown 表格（渲染为三线表）。
- 图：`![图 4.1 图题文字](images/xxx.png)`，路径相对论文目录；图题会排到图下方。
- 公式：行内 `$...$`；行间 `$$ ... \tag{2.1} $$`，`\tag` 就是章.序编号（会排到行末右端并转成 Word 原生公式）。
- 引用文献：正文中直接写 `[1]`、`[3][4]`，与参考文献文件序号对应（表格内的 `[1]` 不算引用）。
- 粗体 `**x**`、行内代码 `` `x` `` 可用；其他 Markdown 语法（脚注、删除线等）不要用。

## 2. 各部分怎么写

### 摘要（最后写，但最重要）
公式："针对…问题（1句背景痛点）→ 本文设计并实现了…（1句总述）→ 采用…架构/方法（2~3句方案要点）→ 测试/实验表明…（2~3句**具体数据**）→ 结论价值（1句）"。
第三人称、无图表公式、无引文编号、300~500字。关键词从题目和正文核心概念中取 3~5 个，外延大的在前。
英文摘要逐句对应中文，用一般现在时叙述系统本身、一般过去时叙述实验动作；"本文"译 this thesis/this paper 保持全篇统一。

### 绪论
背景与意义（痛点→为什么现在做→做成了有什么用）→ 国内外研究现状（分主题小节，每段"谁做了什么[n]→还差什么"，结尾归纳不足引出本文）→ 本文主要工作（编号列出 3~5 条，与后文章节和结论的创新点呼应）→ 组织结构（一段一章）。
现状综述是引用密集区，多数 [n] 应落在这里；引用要有评述，不能只罗列。

### 技术基础章
只写"本文用到且后文要回指"的技术，每节末尾点一句"本系统用它做什么"；与百科式铺陈的区别就在这句话。公式推导控制在支撑正文理解所需的最小集合。

### 需求分析 / 总体设计 / 详细实现
- 需求：功能需求按角色-用例组织（配用例图/用例表），非功能需求给出可验证指标（"加密吞吐 ≥ x MB/s"而非"性能良好"）；安全类论文加威胁分析。
- 总体设计：架构图 + 数据流/时序图 + 数据库 ER 与表结构（三线表）+ 关键机制设计。先图后文逐一解释图中要素。
- 实现：按模块小节，"设计思路 → 关键流程（图/伪代码）→ 实现要点"；贴代码要克制，核心算法伪代码或流程图优先，大段源码放附录。

### 测试章
测试环境（软硬件表）→ 功能测试（用例表：编号/输入/预期/实际/结论）→ 性能测试（数据表+必要图）→ 小结。数字必须与摘要、结论中引用的一致。

### 结论
三段式：工作总结（对应"主要工作"逐条收口）→ 创新点/特色（2~5 条，可编号）→ 不足与展望（诚实但不自毁，展望要具体可行）。不引入新概念、新数据。

### 每章小结
一段 100~200 字，"本章完成了…，为第 x 章…奠定基础"，起承上启下作用。

## 3. 学术文风清单（改稿时逐条对照）

- 全文统一用"本文/本系统"，不用"我/我们/笔者"混用；不用口语（"很/非常/其实/当然"）。
- 结论先行：每段首句给论点，后文给论据；一段只说一件事。
- 数据说话：能给数字不给形容词；数字带单位、有出处（自测注明测试条件，他人成果标 [n]）。
- 术语全篇统一（如"密钥封装"不要一会儿写"密钥包装"）；缩写首次出现给全称，如"密钥生成中心（Key Generation Center，KGC）"。
- 先文后图/表：正文必须先出现"如图2.1所示/见表3.2"，图表紧随其后。
- 图表自明：脱离正文也能看懂；表头有单位；坐标轴有标签。
- 不许出现的：网络用语、感叹号、反问句、"众所周知"、无出处的绝对断言（"XX是最好的"）。
- 引用红线：他人观点/数据/图一律标 [n]；直接翻译改写也算引用。查重前自查连续雷同表述。

## 4. 常见任务的操作路径

- **扩写/改写某章**：读该章 md → 按上面章法调整 → 保持图表公式编号不变或同步更新全链引用 → 跑 `check_thesis.py` 确认没破坏合规。
- **加一张图/表**：确定所在章的下一个空闲编号 → 正文先加"如图x.y所示" → 插入图/表及题名 → 检查该章后续编号是否需要顺延。
- **加参考文献**：加到文献表末尾（新序号），或按正文首次引用位置插入并**全文重排序号**（推荐后者，规范要求按出现顺序）；改完必跑 `check_thesis.py`。
- **润色摘要**：字数卡 300~500，关键词对齐正文，中英对照逐句核对。
- **降重 / 去 AI 味**：先跑 `style_check.py` 拿到「重复片段」和「并列结构」清单 → 按 `paraphrase-and-humanize.md` 的五级策略改写 → 复跑两个脚本，确认没新增 FAIL 且文风基线没漂移。
- **通读审查**：按 `review-checklist.md` 四轮走，输出分级报告（🔴/🟡/🟢）。
- **查重准备**：综述部分改写为自己的归纳语言；公式、标准条文、系统名词不必改。

## 5. 写作时的三条自我约束

写新内容时最容易破的三件事，落笔前先记住：

1. **别写成科普**。技术基础章只写"本文用到且后文要回指"的内容，每节末尾必须有"本系统用它做什么"。
2. **别堆形容词**。这句实测数据能顶一段定性描述："SM9-IBE 封装热态平均 28.5 ms、解封 14.3 ms、SM4-CBC 14.4 MB/s、SM3 45.8 MB/s（浏览器内纯 JS）"。能给数字就给数字。
3. **别把限定条件写没了**。本文的诚实边界（只完成算法示例与工程测试、不等同于商用密码认证或密评；应用服务器与 KGC 属可信控制面；审计链无外部锚点）是**加分项**，不是缺点，任何扩写都不要把它们抹平。
