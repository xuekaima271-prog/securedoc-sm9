# 全文审查与一致性检查

> 触发词：审查、检查一下有没有问题、答辩前帮我看一遍、通读、逻辑通不通、一致性
> 分工：本文档管**内容质量与一致性**（要靠判断的）；`check_thesis.py` 管**合规**（能自动算的）；`style_check.py` 管**文风**（AI 味与节律）。三者一起跑才是完整体检。

## 0. 审查纪律

1. **只审给出的文本**，不脑补论文里没有的内容。
2. **指出具体位置**。"第 3 章 3.2 节第 2 段"，不说"逻辑有问题"。
3. **给可操作的改法**。不说"需要改进"，说"建议改成……"。
4. **分三级**：🔴 必须改 / 🟡 建议改 / 🟢 锦上添花。
5. **不虚假表扬**，也不为凑数硬挑毛病。

## 1. 第一轮：逻辑链完整性

工程实现类论文的骨架：

```
绪论（为什么做）→ 技术基础（基于什么做）→ 需求分析（要做成什么样）
→ 总体设计（怎么做）→ 详细实现（真做了什么）→ 测试（做得怎样）→ 结论（意味着什么）
```

逐条检查：

- [ ] 绪论 1.3「本文主要工作」的每一条，后文是否都有对应章节落地？
- [ ] 需求分析提的每条需求（功能 F1~Fn、非功能、安全），设计/实现/测试里是否都回应了？
- [ ] 设计章画的每个机制，实现章是否都实现了？实现章的模块，设计章是否都有出处？
- [ ] 测试章验的每个点，是否对应前文的设计目标或需求条目？
- [ ] 结论的「工作总结」是否与前文逐条收口，有没有冒出前面没提过的新东西？
- [ ] 每章小结是否真的承上启下，还是套话？
- [ ] 有没有"孤儿内容"——前面提了后面没下文，或后面用了前面没交代的概念？

**本项目要点**：威胁分析（3.3）提的威胁，安全设计（4.4）是否逐条给了对策，测试（6.3）是否逐条验了？这三处形成闭环是本文的加分项，断了会很明显。

## 2. 第二轮：逐章专项

### 摘要
- [ ] 四要素齐不齐：目的 / 方法 / **结果（具体数据）** / 结论
- [ ] 300~500 字（`check_thesis.py` 自动验）
- [ ] 无图表、无公式、无 `[n]` 引文编号
- [ ] **摘要里的数字与测试章完全一致**（最高频的低级错误）
- [ ] 中英摘要逐句对应；英文用一般现在时叙述系统、一般过去时叙述实验

### 绪论
- [ ] 背景有数据/事实支撑，不是纯定性描述
- [ ] 研究现状是**分类组织 + 横向对比**，不是逐篇罗列流水账
- [ ] 每类现状末尾指出了不足/空白，且这个不足正好被本文解决
- [ ] 引用密集且**有评述**（"某方法虽有效，但忽略了 X[n]"），不是"某某做了某某[n]"
- [ ] 1.3 主要工作 3~5 条，与结论创新点一一呼应

### 技术基础
- [ ] 只写了**本文用到且后文会回指**的技术（百科式铺陈是常见毛病）
- [ ] 每节末尾点了"本系统用它做什么"
- [ ] 公式符号都有定义，公式编号连续

### 需求分析 / 总体设计 / 详细实现
- [ ] 功能需求按角色-用例组织，非功能需求**可验证**（"≥ x MB/s"而非"性能良好"）
- [ ] 总体设计先图后文，逐一解释图中要素
- [ ] 设计决策给了依据（为什么选 A 不选 B）——**这是审稿人最爱挑的地方**
- [ ] 实现章贴代码克制；核心算法给伪代码/流程图，大段源码进附录
- [ ] 有"诚实边界"声明（哪些威胁没解决）——本项目已有，保持

### 测试
- [ ] 结构完整：环境 → 功能 → 安全 → 性能 → 小结
- [ ] 不是只堆数据，有分析解读
- [ ] 有对比或基准（国标向量对标就是）
- [ ] 负面/异常结果有解释，不回避
- [ ] 数字与摘要、结论一致

### 结论
- [ ] 工作总结逐条对应前文
- [ ] 创新点 2~5 条，可编号
- [ ] 局限诚实但不自毁；展望**具体可行**（"引入门限化主密钥"而非"未来可进一步研究"）
- [ ] 不引入新概念、新数据

## 3. 第三轮：一致性检查

> 更细的自动化版本见 `style_check.py` 的「术语一致」「自称分布」两项。

### 术语
- [ ] 同一概念全文一种写法。**本项目已发现**：`接收人`(36) vs `接收方`(7)、`审计日志`(11) vs `审计记录`(3)、孤立变体 `分片`(1)
- [ ] 缩写首次出现给全称，如"密钥生成中心（Key Generation Center，KGC）"；此后同章内统一
- [ ] 注意形近但含义不同的词**不要**合并（如「标识密码」IBC 与「标识加密」IBE 是两回事）

### 图表
- [ ] 编号格式统一：本项目用 `图2.1` / `表2.1`（不用 `图2-1`）
- [ ] 图题在下、表题在上；三线表
- [ ] 每个图表都在正文被引用（无孤儿图表）
- [ ] 表头带单位；坐标轴有标签

### 参考文献
- [ ] 标注格式统一为 `[n]`（不用 `(1)` 或上标①）
- [ ] 正文引用 ↔ 文献表双向对应（`check_thesis.py` 自动验）
- [ ] **编号按正文首次出现顺序**排列（规范要求）
- [ ] 条目格式统一（GB/T 7714-2015，见 `format-spec.md` §7）

### 数字与单位
- [ ] 数字用阿拉伯数字，年份写全（2003 年，不写 03 年）
- [ ] 单位统一：`MB/s` 与 `兆字节每秒` 不要混用
- [ ] 同一指标在不同章节的表述方式一致

### 标题与自称
- [ ] 各级标题编号格式统一，命名风格统一（都用名词短语）
- [ ] 自称：`本文`=论文自身，`本系统`=所实现的系统，两者分工清晰；**不出现** 本研究/本工作/本课题/我们
- [ ] 中英文之间空格统一（`style_check.py` 自动验）

## 4. 第四轮：格式合规

交给脚本，人工只核对脚本查不到的：

```bash
python .agents/skills/thesis-writing/scripts/check_thesis.py --src thesis
python .agents/skills/thesis-writing/scripts/style_check.py  --src thesis
```

脚本覆盖：字数、摘要字数、关键词数、文献总数与外文数、序号连续、标题层级与字数、图表编号与先文后图、公式编号、正文 [n] 对应、套话、被动、并列工整度、段落节律、句长、中英混排、跨章重复。

脚本查不到的，人工过：**页眉页脚、目录页码、三线表样式、公式渲染** —— 这四项必须打开生成的 `.docx` 或 PDF 用眼睛看。

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【总览】
🔴 必须修改：X 项    🟡 建议修改：X 项    🟢 锦上添花：X 项
AI 痕迹风险：低 / 中 / 高

【逻辑链评价】
（2~3 句整体判断：闭环有没有断）

【逐章问题】
▸ 第 3 章 系统需求分析
🔴 非功能需求不可验证
   位置：3.2 节第 3 段
   问题："系统应具备较好的并发处理能力"——无法验证
   建议：改为"在 4 核 8 GB 环境下支持 ≥ 50 并发上传，P95 响应 < 500 ms"

【一致性】
（术语/图表/文献/数字的问题，逐条）

【格式】
（脚本输出的 FAIL/WARN + 人工核对结果）

【亮点】
（1~3 条，真实的）
```
